# WorkManagement 重构与迭代路线

> 这份文档不是单纯的学习清单，而是围绕当前 `WorkManagement` 项目制定的一条 **重构 + 迭代 + 带学** 主线。
>
> 目标不是继续堆功能，而是把这个项目逐步演进成一个：
> - 结构更清晰
> - 数据访问更扎实
> - 接口设计更规范
> - 工程化更完整
> - 可以承载后续中间件增强的后端项目
>
> 这条路线默认遵循一个原则：
>
> **先把单体项目打磨扎实，再接更强的工程增强点。**

---

## 一、当前项目定位

当前项目已经不是一个空壳 CRUD 演示，而是一个有明确业务闭环的前后端分离系统：

- 管理员、教师、学生三类角色
- 作业发布、提交、批改、成绩查看等核心流程
- 基础鉴权、角色隔离、前后端联调
- JPA + MySQL 的数据落地
- Vue 3 管理后台页面与交互

这说明当前项目已经具备：

- 业务建模第一层能力
- Spring Boot 分层开发第一层能力
- 登录鉴权与权限控制第一层能力
- 前后端联调第一层能力

但它也暴露出后续最值得继续提升的几个方向：

- 数据访问层还不够“标准后端开发化”
- 接口设计还偏第一层
- 工程边界和配置边界还不够稳定
- 系统设计与性能意识还没有真正落到项目里

所以后续路线不建议继续横向扩栈，而应该围绕当前项目做纵向升级。

---

## 二、总路线设计

后续迭代分为：

- 一条 `主线`
- 一条 `增强线`

### 主线

先把这个项目从“能跑的业务项目”逐步重构成“更规范、可维护、可扩展的单体后端项目”。

主线重点包括：

- 分层职责收束
- DTO / VO / 分页对象整理
- 参数校验与异常边界整理
- 配置外置化
- 数据访问重构
- SQL 能力补强
- 工程化补强

### 增强线

当主线稳定后，再引入一个真正有工程价值的增强点。

增强线优先顺序建议：

1. `Redis`
2. `消息队列 / 异步化第一层`
3. 更进一步的系统设计演进

原则：

- 先补标准后端链路
- 再补中间件与系统增强
- 不提前上微服务、K8s、复杂分布式

---

## 三、阶段划分

整个项目演进建议分成 5 个阶段。

---

## 阶段 1：单体项目规范化

### 目标

先不扩功能，先把当前单体项目整理到一个更稳的状态。

这一阶段要解决的不是“功能缺不缺”，而是：

- 项目结构是否清晰
- 权限判断是否分散
- 异常处理是否粗糙
- 配置是否存在硬编码
- 列表接口是否缺少统一规范
- 项目是否处于稳定可验证状态

### 这一阶段重点改造项

#### 1. 鉴权与配置整理

- JWT 密钥从代码中外置到配置文件 / 环境变量
- token 提取逻辑统一，不在多个地方重复手写
- 梳理拦截器职责，避免控制器层重复做同类校验
- 为后续权限进一步收束预留空间

#### 2. 异常体系整理

- 区分：
  - 业务异常
  - 权限异常
  - 参数异常
  - 系统异常
- 不再大量依赖 `RuntimeException` 直接抛错
- 统一异常响应格式与错误码语义

#### 3. 接口对象规范化

- 梳理 DTO / VO / 实体对象边界
- 给列表接口补：
  - 分页请求对象
  - 分页返回对象
  - 基础筛选对象
- 避免接口直接暴露“凑合能用”的数据结构

#### 4. 测试与项目状态清理

- 移除故意失败的测试
- 保证后端测试和前端构建处于正常状态
- 让项目进入“可以继续稳定迭代”的基础状态

### 这一阶段要练到的能力

- Spring Boot 项目结构感
- 配置管理意识
- 异常边界意识
- 接口规范意识
- 工程稳定性意识

### 阶段产出

做完后，这个项目应该至少达到：

- 项目能稳定启动与构建
- 鉴权、异常、配置比现在更规范
- 基础接口结构开始具备统一风格
- 后续数据访问重构有更稳的地基

---

## 阶段 2：数据访问层重构

### 目标

这是整条路线里最重要的一阶段。

目标是把当前项目的一部分核心查询，从“偏 JPA 仓库方法拼接”升级成“更可控、更接近标准后端开发链路”的实现方式。

### 为什么这一阶段最重要

因为当前项目虽然已经完成了业务闭环，但数据访问层更多是：

- 基于 JPA Repository 方法名查询
- 在 Service 层做聚合和结果拼装
- 存在一些全量查询再过滤、再组装的处理方式

这说明当前项目能支撑你继续提升的最值钱方向，不是再加几个页面，而是：

- SQL
- MyBatis
- 查询设计
- 分页
- 动态条件
- 映射与结果结构设计

### 建议优先重构的模块

#### 1. 作业列表模块

适合练：

- 分页查询
- 条件筛选
- 课程 / 教师维度组合查询
- 查询结果映射

#### 2. 提交列表模块

适合练：

- join 查询
- 教师 / 学生维度隔离
- 分页与筛选
- 状态字段处理

#### 3. 教师统计模块

适合练：

- group by
- count
- topN
- 聚合统计查询
- 用 SQL 直接表达业务统计，而不是全量查询后在内存里拼

### 这一阶段建议方式

- 不需要一次性把 JPA 全部迁掉
- 可以采用“局部替换”的方式
- 先挑 1~2 个最能训练 SQL 的模块，用 MyBatis 单独重写
- 保留其他模块暂时继续使用 JPA

### 这一阶段要练到的能力

- SQL 查询能力
- MyBatis 基础使用
- 动态 SQL
- 分页查询
- 数据映射设计
- 从“会查数据”到“会设计查询”的能力

### 阶段产出

做完后，你应该能明确说清：

- 为什么这个模块更适合自己写 SQL
- 为什么不能继续全部依赖 findAll 之后再处理
- MyBatis 和 JPA 在这个项目里各自适合什么场景
- 一个标准列表接口的查询链路该怎么设计

---

## 阶段 3：接口设计升级

### 目标

把接口从“能返回数据”升级成“更像真实项目里的接口”。

### 重点改造方向

#### 1. 分页与筛选体系

统一设计：

- pageNum
- pageSize
- 查询条件对象
- 列表结果对象
- total + list 的标准响应结构

#### 2. 返回结构与错误语义

- 统一 code / message / data 的边界
- 区分前端真正需要提示的错误和系统内部错误
- 让前端层不需要猜接口语义

#### 3. 权限边界表达

- 明确“谁能调用什么接口”
- 明确“谁能看到哪些数据”
- 明确权限判断应该落在哪一层

#### 4. DTO / VO / Entity 边界强化

- 请求对象只负责接参数
- Entity 只负责持久化
- VO / Response 只负责返回前端
- 避免职责混杂

### 这一阶段要练到的能力

- 接口设计意识
- 分页接口设计能力
- 权限边界思维
- 结构抽象能力
- “为什么这样设计”的表达能力

### 阶段产出

做完后，你不仅能写接口，还能解释：

- 为什么分页接口要这样返回
- 为什么不直接把数据库表结构原样暴露给前端
- 为什么查询条件要单独抽对象
- 为什么权限不应该散落在每个地方随手判断

---

## 阶段 4：工程化补强

### 目标

把项目从“本地能跑”推进到“更像一个可持续维护的项目”。

### 重点改造方向

#### 1. 测试最小闭环

- 保证基础测试可运行
- 给核心业务链路补最小测试
- 至少覆盖：
  - 登录
  - 权限访问
  - 核心列表 / 提交流程中的关键接口

#### 2. 配置分环境

- 本地开发配置
- Docker / 部署配置
- 敏感信息外置
- 配置项命名统一

#### 3. Docker 与运行链路整理

- 梳理前后端与数据库启动方式
- 明确开发环境与部署环境差异
- 让 README 和实际运行方式尽量一致

#### 4. 日志与排错意识

- 引入基础日志思维
- 关键错误路径保留排错信息
- 避免所有问题都只能靠猜

### 这一阶段要练到的能力

- 工程调试能力
- 项目维护能力
- 运行环境理解
- 配置与部署第一层认知

### 阶段产出

做完后，你应该能更自信地回答：

- 项目怎么启动
- 配置怎么切换
- 出错先看哪里
- 如何证明一个改动没有把系统搞坏

---

## 阶段 5：增强线接入

### 目标

当前面几个阶段做稳之后，再给这个项目接一个真正有工程意义的增强点。

这里不建议为了“堆技术栈”硬加，而是要让增强点真正服务于系统演进。

### 优先增强方向：Redis

#### 适合接入的场景

- 教师仪表盘统计缓存
- 热门统计结果缓存
- 频繁读取但变更不高的数据缓存
- 登录态 / token 黑名单第一层方案

#### 通过 Redis 要练的不是“会用缓存”这么浅

而是：

- 为什么这里适合缓存
- 缓存和数据库怎么分工
- 缓存失效怎么处理
- 缓存一致性第一层怎么理解

### 第二增强方向：异步化 / 消息队列第一层

后续可以考虑的场景：

- 提交作业后异步生成统计
- 异步通知教师有新提交
- 批量统计类任务异步化

重点不是为了把项目搞复杂，而是为了训练：

- 同步与异步的边界
- 为什么要解耦
- 什么场景适合引入消息队列

### 这一阶段要练到的能力

- 中间件使用场景判断
- 缓存设计第一层
- 异步解耦第一层
- 系统扩展意识

### 阶段产出

做完后，你应该能把这个项目从“标准业务项目”讲到“带一点系统设计意识的项目”。

---

## 四、推荐推进顺序

推荐按下面顺序推进：

1. `阶段 1：单体项目规范化`
2. `阶段 2：数据访问层重构`
3. `阶段 3：接口设计升级`
4. `阶段 4：工程化补强`
5. `阶段 5：增强线接入`

这个顺序背后的逻辑是：

- 先稳结构
- 再补数据访问硬能力
- 再升级接口设计
- 再补工程化
- 最后引入中间件增强

不建议上来直接做：

- 微服务拆分
- Spring Cloud
- K8s
- 复杂分布式设计
- 大规模性能优化

因为当前项目还没走到那个水位。

## 五、带学方式说明

这条路线默认不是“我给完整答案，你照抄”。

后续如果按这条路线推进，建议采用这样的方式：

### 1. 每次只推进一个改造点

例如：

- 先只改 JWT 配置外置
- 或先只改异常体系
- 或先只改提交列表分页查询

不同时展开太多方向。

### 2. 每次推进都分三步

#### 第一步：先确认问题

要先回答：

- 当前这块最大问题是什么
- 为什么它影响可维护性 / 可扩展性
- 为什么现在优先改它

#### 第二步：再拆方案

要先讲清：

- 改动落在哪一层
- 会影响哪些文件
- 新旧方案差别是什么
- 为什么不用别的改法

#### 第三步：最后动手实现

实现完之后，不只看能不能跑，还要复盘：

- 这次学到的技术点是什么
- 这次最核心的设计取舍是什么
- 如果以后换一个模块，能不能迁移这套思路

### 3. 每个阶段都要回答 3 个问题

这是后续学习和复盘时的固定问题：

1. 这里最大的瓶颈是什么？
2. 我是怎么解决的？
3. 为什么这样设计？

如果这 3 个问题答不出来，说明这一步还没有真正学到位。

## 六、第一阶段建议起点

如果从明天开始正式入手，建议从 `阶段 1` 开始，并且第一刀不要切太大。

### 第一阶段可选起点

可以从下面四个方向里选一个开始：

#### 方案 A：鉴权与配置整理

适合练：

- 配置外置化
- 安全意识
- 拦截器职责
- token 处理边界

#### 方案 B：异常体系整理

适合练：

- 业务异常设计
- 全局异常处理
- 错误语义表达
- 后端接口一致性

#### 方案 C：接口分页与筛选规范化

适合练：

- 分页对象设计
- 列表接口抽象
- DTO / VO 边界
- 接口契约意识

#### 方案 D：测试与项目状态清理

适合练：

- 工程稳定性
- 最小测试闭环
- 项目维护意识

### 我的建议

如果按“收益 / 学习价值 / 对后续帮助”综合排序：

1. `鉴权与配置整理`
2. `异常体系整理`
3. `测试与项目状态清理`
4. `接口分页与筛选规范化`

如果按“最容易快速起步”排序：

1. `测试与项目状态清理`
2. `鉴权与配置整理`
3. `异常体系整理`
4. `接口分页与筛选规范化`

## 七、一句话总结

这个项目后续最值得走的，不是继续横向堆功能，而是按下面这条路逐步升级：

**先把单体结构打稳，再补 SQL / MyBatis 和接口设计，再补工程化，最后接 Redis / 异步化，把它从“业务项目第一层”推进到“更像真实后端项目”的水位。**

## 八、后续使用方式

等正式开始推进时，每次都可以直接围绕这份文档中的某一阶段开工，例如：

- “从阶段 1 的鉴权与配置整理开始”
- “先做阶段 2 的提交列表 MyBatis 重构”
- “先拆阶段 3 的分页接口规范”

后续推进时，不额外追求大而全，只围绕当前这一个项目，一刀一刀往前改。
