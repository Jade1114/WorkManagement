# Cloud 后续推进清单

> 这份文档用于记录当前 `cloud/` 学习版工程在后续几轮中的推进顺序，避免在已经具备较完整模块能力后再次发散。

## 当前已完成

### 基础设施
- Nacos 注册发现
- Nacos Config（JWT / DB）
- Gateway 路由
- JWT 最小鉴权
- 统一 401 JSON
- 身份透传

### 业务模块
- `user-service`
  - 注册 / 登录 / 当前用户 / 改密码
  - 学生列表 / 管理员用户列表 / 管理员更新用户
  - 内部用户校验 / 摘要 / 数量统计
- `education-service / course`
  - 课程列表 / 课程作业数量统计 / 创建 / 更新 / 删除
- `education-service / assignment`
  - 创建作业 / 作业列表 / 课程作业列表 / 待提交作业列表
- `education-service / submission`
  - 学生提交 / 提交列表 / 提交总览 / 批改 / 我的提交列表 / 我的提交详情
- `education-service / teacher dashboard`
  - stats / recent assignments / recent submissions / top submitters / data screen

## 下一阶段主线

### P0：文档整理
- 更新 `cloud/README.md`
- 整理已迁模块清单
- 整理待处理复杂模块清单
- 明确当前角色语义与接口边界

### P0：前后端对齐
- 统一前端最终走的新路径
- 前端统一切到 `/user/**` 与 `/education/**`
- 清理剩余旧接口与页面侧旧调用
- 对齐前端真正需要的返回字段

### P1：复杂业务规则专项
建议后续按专题推进，而不是继续补大量同质化接口：
- 作业截止后是否允许提交
- 已提交后是否允许重复提交 / 覆盖提交
- 已批改后是否允许再次提交
- 教师批改后是否允许再次修改评分
- 删除课程后关联作业 / 提交的处理策略

### P1：权限边界精修
- admin 的只读 / 管理范围进一步收清
- teacher 数据范围是否始终只限自己域内
- student 相关数据是否需要更细的课程范围约束

### P2：工程结构继续收口
- 收掉剩余过渡期接口命名与页面调用
- 收 service 中开始变重的聚合逻辑
- 判断哪些测试味道重的入口要下掉
- 逐步降低“迁移过渡态”代码比例

### P2：关键链路测试补强
后续优先补少量关键集成测试：
- 登录 / Gateway 鉴权
- assignment 创建
- submission 提交 / 批改
- student 查询自己的提交
- teacher dashboard 关键统计接口

## 当前不建议
- 一次性整体迁完单体后端
- 过早引入新的 Cloud 组件（熔断、分布式事务等）
- 过早做复杂公共抽象
- 在前后端未对齐前就大量精修细碎业务规则

## 当前主线原则
- 先把已迁模块说清楚，再继续扩复杂能力
- 先完成前后端对齐，再精修复杂业务规则
- 对重复度高的业务批量推进，对复杂规则按专项推进
- 每完成一个清晰阶段，就进行一次复盘与提交
